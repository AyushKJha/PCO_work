1. Product boundary

AgentPGO is an offline control-plane and experiment system. It does not sit in the customer’s production inference path and never automatically deploys a model assignment. The SDK and generic OTLP endpoints observe calls; the API records durable work; workers execute controlled experiments; the result is an exportable recommendation.

Failure isolation: if the optimizer, worker, or dashboard is unavailable, the customer agent continues to run. The only V1 side effect is telemetry export and queued experiment work.

3. Telemetry ingestion and profiling

The canonical internal shape is an OpenTelemetry GenAI span. The API accepts OTLP JSON at /v1/traces and the compatibility alias /v1/otlp/v1/traces. Span identity is (project_id, trace_id, span_id); duplicates are ignored. The server recursively redacts prompt/output/content/credential-like keys and stores raw_span as an empty object unless explicit opt-in is enabled.

4. Optimization execution path

An optimization run is a durable state machine. A request validates the candidate pool and budget, stores a versioned JobPayload, writes an outbox event, and publishes a small SQS message. The worker does not trust queue state as the source of truth; it loads the PostgreSQL job and claims it with a lease.

stateDiagram-v2 [*] --> queued queued --> running: claim lease running --> evaluating: start candidate evaluation evaluating --> validating: all candidates checkpointed validating --> completed: gates pass; recommendation persisted running --> queued: bounded retry evaluating --> queued: transient failure validating --> queued: transient failure queued --> failed: retry limit / budget failure running --> failed: non-retryable failure evaluating --> failed: spend cap / invalid metrics validating --> failed: no eligible candidate completed --> [*] failed --> [*]

Staged search

  1. Baseline: evaluate the known configuration over the complete eval set.
  2. Sensitivity: vary one node/model assignment at a time and record quality, cost, and latency deltas.
  3. Beam: keep only the best bounded configurations instead of enumerating the full Cartesian product.
  4. Successive halving: run cheap early samples, discard weak candidates, and reserve the full suite for finalists.
  5. Gate and recommend: apply customer constraints, calculate paired confidence intervals, select a Pareto-eligible candidate, and persist an exportable recommendation.

5. Authoritative data model

Every customer-owned row carries organization_id. Project-scoped keys inject an authorized project into every resource lookup. Jobs and candidate results are durable; process memory is never used as a source of truth.

6. Worker durability and failure semantics

sequenceDiagram participant Q as SQS participant W as Worker participant DB as PostgreSQL participant P as Provider Q->>W: receive job_id, visibility timeout starts W->>DB: claim queued/expired job with lease token W->>DB: reserve estimated spend FOR UPDATE W->>P: execute candidate with bounded provider policy W->>DB: record candidate result, usage, cost, checkpoint W->>DB: release reservation, persist aggregate W->>DB: persist OptimizationResult, transition completed W->>Q: acknowledge only after durable completion Note over W,Q: heartbeat renews DB lease and SQS visibility during long calls Note over P,DB: provider idempotency is required for true exactly-once billing
  • At-least-once processing: SQS may redeliver. A unique candidate identity and checkpoint mean completed candidates are not persisted twice.
  • Lease fencing: mutations include the worker identity and lease token; a stale worker cannot overwrite a newer claim.
  • Spend reservation: estimated cost is reserved atomically before an external call and reconciled to actual usage afterward.
  • Outbox boundary: the database event records intent so a reconciler can re-publish if a direct queue publish fails.
  • Honest guarantee: a crash after a provider succeeds but before the receipt commits can duplicate external spend unless the provider honors an idempotency key.

7. AWS deployment topology

The current testing deployment uses one ECS Fargate API service and one worker service, fronted by an ALB. RDS is private; S3 and SQS are IAM-controlled. The current ALB is temporary HTTP because no user-owned domain/ACM certificate was available at deployment time.

8. Security and privacy boundaries

flowchart LR Key[API key] --> Hash[hashed key lookup] Hash --> Tenant[organization + optional project scope] Tenant --> Authz[resource authorization] Authz --> Redact[recursive content/credential redaction] Redact --> Store[(PostgreSQL / S3)] Secret[provider secret] --> KMS[KMS encryption] KMS --> Runtime[task runtime retrieval] Runtime --> Provider[provider call] style Key fill:#3b2d1c,stroke:#ffc978,color:#fff style Store fill:#183957,stroke:#69a7ff,color:#fff
  • Prompts, completions, tool payloads, and authorization-like attributes are off by default; only operational metadata is needed for profiling.
  • Request sizes, candidate counts, evaluation cases, and configuration bytes are bounded at the API edge.
  • API keys are hashed at rest and project-scoped keys cannot create or access another project.
  • Provider keys are task secrets, not source files or queue messages.
  • The deployed test endpoint is HTTP-only and must not receive customer data. HTTPS with a user-owned domain is the production gate.

What a recommendation means

A recommendation is a persisted, reproducible experiment result—not an automatic routing policy. It contains the selected candidate configuration, measured quality/cost/latency, gate status, dataset/run metadata, and a portable export. A developer reviews it and changes their own agent configuration when ready.
